# 2026-11-02: Sourcify API v2, answer by answer

Audience: whoever changes the Sourcify client (`packages/explorer-verify/src/backends/sourcify.ts`).
This note records every Sourcify answer the client maps, with its source. It extends the Sourcify
section of [2026-11-02-explorer-apis.md](2026-11-02-explorer-apis.md#sourcify-api-v2). Each claim
names its source; the links, the local runs and the recorded responses are listed under
[Sources](#sources). "Live" marks an answer to a request sent on 2026-11-02 and recorded with its
headers and body. The answers the client maps are the fixtures in
`packages/explorer-verify/test/fixtures/sourcify/`, whose `source` field gives the time of each.
"Spec" marks the OpenAPI document and "source" the server code, both listed below.

## Version checked

`GET https://sourcify.dev/server/version` reported server 4.2.0 at commit
[`189cd726`](https://github.com/argotorg/sourcify/tree/189cd726f7ed8fb3d2f503402d5c133e0f50e1fd)
(live, 2026-11-02; again with curl 8.7.1 on 2026-11-03). The OpenAPI document at
`https://sourcify.dev/server/api-docs/swagger.json` is APIv2, version 2.1.0 (read on 2026-11-02).
The v1 API was switched off on 2026-07-07 ([API docs](https://docs.sourcify.dev/docs/api/), read
on 2026-11-02); `GET /check-by-addresses` and `POST /verify` answered 404 (live).

## Calls

| Call       | Request                                                                                                                       | Responses                                                                                                                                                                  |
| ---------- | ----------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Lookup     | `GET /v2/contract/{chainId}/{address}`                                                                                        | 200 `{ match, creationMatch, runtimeMatch, chainId, address, verifiedAt, matchId }` (live). 404 with all three match fields `null` (live). 400 `unsupported_chain` (live)  |
| Submit     | `POST /v2/verify/{chainId}/{address}`, JSON `{ stdJsonInput, compilerVersion, contractIdentifier, creationTransactionHash? }` | 202 `{ verificationId }` (live). 400 `invalid_parameter` (live). 409 `already_verified` (live). 429 `too_many_requests` or `duplicate_verification_request` (spec, source) |
| Job status | `GET /v2/verify/{verificationId}`                                                                                             | 200 with `isJobCompleted`, `contract`, and `error` on failure, even when the job failed (live). 404 `job_not_found` (live)                                                 |

- `stdJsonInput` is an object, not a JSON string. Only the top-level fields that Sourcify stores
  are accepted: `language`, `sources` and `settings`, plus a Vyper field. Sourcify overrides
  `outputSelection` (spec).
- `compilerVersion` must match `^v?\d+\.\d+\.\d+.*$`, so the long form passes with or without `v`
  (spec).
- `creationTransactionHash` is optional; the spec says it makes fetching the creation bytecode
  reliable (spec).
- Errors share one body: `{ customCode, message, errorId }` (live). A failed job carries the same
  fields under `error`, and can add large fields such as `onchainRuntimeCode` and
  `recompiledCreationCode` (live: `contract_not_found_in_compiler_output` and `no_match` jobs).
- `chainId` is a string in every lookup and job body (live).

## Match values

- `match`, `creationMatch` and `runtimeMatch` are each `exact_match`, `match` or `null` (spec).
- The top-level `match` is `exact_match` when the creation or the runtime match is exact, `match`
  when either is a partial match, and `null` otherwise (source,
  `services/server/src/server/services/utils/util.ts`, `getTotalMatchLevel`).
- "Exact match" means the metadata hash matches too; "match" means everything but the metadata
  hash matches ([Sourcify docs](https://docs.sourcify.dev/docs/exact-match-vs-match/), read on
  2026-11-02).

## Job states seen

| State                   | Body                                                                                                     | Source                            |
| ----------------------- | -------------------------------------------------------------------------------------------------------- | --------------------------------- |
| Pending                 | `isJobCompleted: false`, `contract` with all match fields `null`                                         | live, `job-pending`               |
| Completed, exact        | `isJobCompleted: true`, `contract.match`, `creationMatch` and `runtimeMatch` `exact_match`               | live, `job-exact-match`           |
| Completed, partial      | `contract.match` `match`                                                                                 | live, `job-match`                 |
| Completed, rejected     | `error.customCode` `no_match` or `contract_not_found_in_compiler_output`, match fields `null`            | live, `job-no-match` and others   |
| Completed, not deployed | `error.customCode` `contract_not_deployed`, for an address with no code; the job ended within one second | live, `job-contract-not-deployed` |
| Unknown job             | 404 `job_not_found`                                                                                      | live, `job-not-found`             |

Every job on the five testnets of 2026-11-02 (Sepolia, Arbitrum Sepolia, Base Sepolia, Avalanche
Fuji, Polygon Amoy) completed within about one second of the submit, a few seconds after the
deployment. None ended with `contract_not_deployed` (live).

## Error codes

From the server and library source at commit `189cd726`:

- Rejects the source for good: `no_match`, `bytecode_length_mismatch`, `compiler_error`,
  `missing_source`, `missing_or_invalid_source`, `invalid_compilation_target`,
  `contract_not_found_in_compiler_output`, `runtime_bytecode_not_found_in_compiler_output`,
  `invalid_compiler_version`, `unsupported_compiler_version`, `invalid_language`,
  `unsupported_language`, `compiled_bytecode_is_zero`, `onchain_bytecode_is_zero`,
  `extra_file_input_bug`.
- May clear up on a later submit: `internal_error`, `job_abandoned` (the server message says "You
  can resubmit"), `compiler_timeout`, `compiler_out_of_memory`, `no_compiler_output`,
  `cannot_fetch_bytecode`, `onchain_runtime_bytecode_not_available`,
  `onchain_creation_bytecode_not_available`, `contract_not_deployed` (it may be RPC lag right after
  a deployment).
  The client throws `verification-inconclusive` for these, since polling the finished job again
  gives the same answer ([decision 0011](../decisions/0011-verification-inconclusive-error.md)).
- Not classified until a recorded response shows what it means: every other code, among them
  `creation_bytecode_match_error`, `metadata_not_set` and the `*_cbor_auxdata_*` codes.

## Already verified and upgrades

- Submit answers 409 `already_verified` only when the contract already has an exact match on both
  creation and runtime (source, `services/server/src/server/apiv2/middlewares.ts`). A resubmit after
  an exact verification got that 409 on all five testnets (live).
- For a contract with a partial match, a new submit is accepted with 202 and the job decides
  (live). A job whose result is not better than the stored match ends with `error.customCode`
  `already_verified` (source, `VerificationService.ts`). No such job was recorded.
- Submitting exact sources over a partial match returned 202, and the job upgraded the contract to
  `exact_match` with the same `matchId` (live, Base Sepolia, `58142467`; the lookup still showed
  that `matchId` with curl 8.7.1 on 2026-11-03).
- A wrong-source submit for a contract that already had a partial match became a job that ended
  with `no_match` (live).

## Caching

- A 200 lookup carried `cache-control: public,max-age=3600` and an `age` header (live; again with
  curl 8.7.1 on 2026-11-03). 404 and 400 lookups and job status answers carried no
  `cache-control` (live). A lookup can therefore return a match grade up to an hour old; a "not
  verified" answer is not cached.
- After the upgrade above, a cached `?fields=all` lookup still showed the old partial `match`
  (live). The client reads the lookup without `fields=all` and treats a job result as newer than a
  lookup.

## Forwarding to other explorers

Completed jobs carried `externalVerifications`, with an entry per explorer (live):

- `etherscan`: a job id, `VERIFIER_ALREADY_VERIFIED`, or an error such as a daily limit.
- `blockscout` and `routescan`: `verificationId`, `statusUrl`, `explorerUrl` and `contractApiUrl`.

A Sourcify submit can therefore verify the contract on Etherscan as a side effect: on Polygon Amoy,
Etherscan's `getsourcecode` showed the contract verified after the Sourcify submit alone (live). The
Etherscan client must accept "already verified". `VerifyResult` does not carry these entries in
M1; whether it should is open.

## Linked libraries

For a contract compiled without libraries and linked afterwards, as Foundry and Hardhat do, a
submit with the library address in `settings.libraries` gave `match` on creation and runtime; the
same submit with `"libraries": {}` gave `exact_match` (live, Arbitrum Sepolia, 2026-11-03,
[probe E of the M2 live probes](2026-11-03-m2-live-probes.md#e-a-contract-linked-to-an-external-library)).
Solidity's metadata includes
`settings.libraries`, so the input with addresses compiles to another metadata hash than the
deployed code.

## CORS

Every answer above carried `access-control-allow-origin: *`. A preflight for `POST` with
`content-type` returned 204, allowed methods `GET,HEAD,PUT,PATCH,POST,DELETE` and the header
`content-type` (live).
