# 2026-11-04: live matrix results

Audience: maintainers and contributors who need to know how the built package behaves against real
explorers today, and which answers the unit fixtures did not hold. Assumes the cases and the plan
format in [testing.md](../testing.md#live-matrix).

`scripts/live-matrix.ts` ran once, from 21:45:59 to 22:48:55 UTC on 2026-11-04, against public
testnets and the local fake explorer. 41 cases ran; 37 gave the expected result and 4 did not. Two
of the four are one gap in the Routescan client, fixed on 2026-11-05 (#164). The other two are an explorer-side failure that
stopped the cross-explorer case from testing anything.

## Setup

- The core package at this change, built with `pnpm run build` (version field `0.0.0`), on
  Node.js 24.21.0.
- Contracts compiled and deployed with Foundry `forge` 1.8.1 and solc `0.8.24+commit.e11b9ed9`,
  optimizer on with 200 runs, `evmVersion` `cancun`, `bytecodeHash` `ipfs`. Each source file has a
  comment naming the run and its label, and a constant `MARK` with a value no other contract uses,
  so no explorer could match it from an earlier contract or call it a Similar Match.
- Each contract takes `(address owner_, string greeting_)` and was deployed with the deployer
  address and `"explorer-verify live matrix"`.
- The deployments went through `forge script` with `--skip-simulation`, so the node estimated the
  gas.
- Deployer: `0x9d087fC03ae39b088326b67fA3C788236645b717`.
- Keys: the maintainer's Etherscan key for the two `etherscan-v2` targets. No Routescan key: both
  Routescan targets used the keyless tier. The `etherscan-compatible` target used a dummy key against
  the local fake explorer, because no public standalone explorer answers
  ([standalone explorer note](2026-11-04-etherscan-compatible-client.md)). That target reused the
  contract files of SrcSep1 and SrcSep3; the fake checks a submission against them and reads no
  chain.
- Address with no code, for case 5: `0x000000000000000000000000000000000066e604` (`cast code`
  answered `0x` on all three chains, forge 1.8.1, 2026-11-04).

## Findings

### Routescan: a wrong source threw `unknown-state` instead of giving `failed`

On both Routescan chains, the status of a submit whose source had one digit changed was:

```json
{
  "status": "0",
  "message": "NOTOK",
  "result": "Error: Compilation successful, but bytecode does not match with deployed bytecode for address 0xA7B0158753812cDF1905d70802AF3BDDDe934A57, please check your parameters"
}
```

The client maps only Etherscan's `Fail - Unable to verify` prefix to a rejected job, so this text
falls through to `unknown-state`. The call throws and is never read as verified, so R-FLOW-4's
safety holds, but the caller gets an unknown state for a definitive rejection, where R-FLOW-4 asks
for `failed` with the explorer's reason. This is a gap in the client's mapping, not a fault of the
matrix. The answer is a fixture,
`packages/explorer-verify/test/fixtures/routescan/2026-11-04-checkverifystatus-bytecode-mismatch.json`.

Fixed on 2026-11-05: [issue #164](https://github.com/aelmanaa/explorer-verify/issues/164), merged
in pull request #177, maps this answer to `failed` with its text as the reason, and
`routescan.test.ts` checks it with that fixture. The two Routescan case 4 rows below show the
behaviour of the run, before the fix.

### Cross-explorer forwarding did not reach Etherscan

Case 7 verified each contract on Sourcify, then looked it up on Etherscan every 20 s for up to
300 s. Sourcify verified both contracts. Its job answer listed its forwarding to other explorers,
and the Etherscan entry was an error:

```json
"etherscan": { "error": "Daily limit of 500 source code submissions reached" }
```

The limit appears to be on the key Sourcify uses to forward, not on the maintainer's key, for two
reasons: the error came inside Sourcify's job answer, from a request the matrix did not send, and
the maintainer's key verified the same contracts on Etherscan an hour later in the same case. On Sepolia the same answer listed Routescan and Blockscout jobs; on
Arbitrum Sepolia, Blockscout only. The job answer is now a fixture,
`packages/explorer-verify/test/fixtures/sourcify/2026-11-04-job-exact-match-etherscan-forward-limit.json`.

On each chain, Etherscan's lookup answered "not verified" 14 times, from about 21:46:44 to
21:51:10 UTC. The run paused from 21:51 to 22:48 UTC, which is why both case 7 rows show about
3,735 s. After the pause, one more lookup answered "not verified", so `verify()` submitted. The
Sepolia row lists 16 `getsourcecode` requests: the 14, the one after the pause, and the lookup
inside that `verify()`. The Arbitrum Sepolia row lists 18: two more, because Etherscan answered two
of them with its per-second rate limit and the library sent them again. Then `verify()` submitted
and Etherscan verified the contract in this call: the result was `verified`, not `already-verified`.
The library behaved as specified. The case tested nothing about the library on this day, because
the forwarding it depends on failed. Run it again on a day when Sourcify's forwarding works; the
issue cites one on Polygon Amoy on 2026-11-02.

### Answers the fixtures did not hold

- Etherscan, `checkverifystatus` for a wrong source:
  `Fail - Unable to verify. Compiled contract deployment bytecode does NOT match the transaction deployment bytecode.`
  The only earlier fixture with this prefix was a documented one, not a recording. Recorded as
  `packages/explorer-verify/test/fixtures/etherscan/2026-11-04-checkverifystatus-fail-bytecode-mismatch.json`;
  `etherscan.test.ts` checks it maps to `failed` with that text.
- Etherscan answered `Max calls per sec rate limit reached (3/sec)` to `getcontractcreation`, as it
  already had to `getsourcecode` and `verifysourcecode`. The library retried and went on.
- Sourcify, a job answer whose forwarding list holds an error: see above.
- Routescan, the bytecode mismatch: see above.

### What else the run showed

- Sourcify and Etherscan both verified a contract whose `verify()` call was aborted right after the
  submit; `checkStatus()` in a new process, given only the handle string, read the result
  (R-FLOW-5). Routescan did too, on both chains.
- A second `verify()` sent only lookups on every backend: no submit (R-FLOW-1).
- Without the Etherscan key, `verify()` threw `missing-api-key` before any request on both chains,
  and the key appeared in no output (R-SEC-1).
- `verify()` without `constructorArgs` read the creation code from `getcontractcreation` and
  Etherscan verified the contract with the derived arguments, on both chains (R-IN-3).
- Routescan on Sepolia (chain 11155111, network `testnet`) verified like Fuji. The routing table
  lists no Routescan rows, so both targets set `route.apiUrl`, and the results carry no
  `explorerUrl`.
